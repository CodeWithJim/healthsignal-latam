# Spec-Driven Development: HealthSignal LATAM (RISA Data V1.0)

## 1. Context, Scope, and System Purpose
* **Event:** CIP Hackathon - Area 1 (Health and Data Intelligence).
* **Challenging Entity / Scenario:** Andean Integrated Health Network (RISA), a synthetic healthcare ecosystem of 1,000 patients simulating a fragmented Latin American healthcare network[cite: 1, 3, 4].
* **Operational Problem:** Ingesting and normalizing heterogeneous, disparate-frequency data (ranging from continuous vital signs and wearables to sporadic laboratory events), handling noise, missing values, and intermittent connectivity.
* **Purpose:** Build a decision-support system to **detect, prioritize, and explain** early clinical risk signals (avoiding false alarms due to context or device artifacts), without issuing autonomous diagnoses[cite: 3, 4].

---

## 2. End-to-End Software Architecture (Processing Layers)

To comply with the principles of auditability, traceability, and separation of concerns, the architecture follows a sequential 5-layer pipeline:
[ RISA Data V1.0 (Massive CSV Files) ] │ ▼ ┌─────────────────────────────┐ │ 1. RAW Layer (Immutable) │ ──► Stores original files without alterations. └──────────────┬──────────────┘ │ ▼ ┌─────────────────────────────┐ │ 2. CLEAN Layer (Cleaning) │ ──► Handling nulls, misalignment, and unit harmonization[cite: 3, 4]. └──────────────┬──────────────┘ │ ▼ ┌─────────────────────────────┐ │ 3. FEATURES Layer (Temporal)│ ──► Sliding windows and trends respecting T_available <= T. └──────────────┬──────────────┘ │ ▼ ┌─────────────────────────────┐ │ 4. MODEL / SCORING Layer │ ──► Deterministic/statistical prioritization engine and traces. └──────────────┬──────────────┘ │ ▼ ┌─────────────────────────────┐ │ 5. EXPORT & VALIDATION │ ──► Automatic generation and testing via validate_submission.py. └─────────────────────────────┘

## 3. Technology Stack and Justification * **Backend / Data Processing (Python):** Selected as the standard analytical language in healthcare, guaranteeing absolute compatibility with the hackathon's official validation script (`validate_submission.py`)[cite: 5]. * **Massive Tabular Manipulation (Polars / Pandas):** Efficiently processes dense time series (such as `vital_signs.csv` and `wearable_observations.csv`)[cite: 2, 3] with low memory consumption. * **Intermediate Storage (Apache Parquet / Local SQLite):** Maintains the immutability of the RAW Layer[cite: 4] while accelerating analytical queries between phases. * **User Interface / Dashboard (Next.js with TypeScript + Tailwind CSS):** Offers superior performance for interactive visualization of patients, temporal evolution charts, and evidence traces. * **Automation & CI/CD (GitHub Actions):** Automatically executes linters, unit tests, and the official submission validator on every repository update[cite: 2, 4, 5]. --- ## 4. Business Rules and Technical Constraints 1. **Strict Temporal Control (Anti-Temporal Leakage):** - Separates the physiological timeline from the operational timeline[cite: 4]. - Any feature or decision at instant $T$ can only use information where $T_{available} \le T$[cite: 4]. 2. **Quality and Context Management:** - Missing data are not assumed to be zero or normal; they require defensible imputation[cite: 4]. - Isolated anomalies are contrasted with connectivity events (`connectivity_events.csv`)[cite: 2, 3] and physical context to filter out false alerts caused by physical activity or hardware noise[cite: 3, 4]. 3. **Preservation of Identifiers:** `patient_id` and original record IDs are preserved to guarantee end-to-end traceability[cite: 4]. --- ## 5. Output Contracts and Strict Validation The solution must export two CSV files under the exact specifications validated by `validate_submission.py`[cite: 4, 5]: ### A. `signals.csv` * **Mandatory columns:** `signal_id`, `patient_id`, `decision_datetime`, `risk_score`, `priority_level`, `evidence_start`, `evidence_end`, `explanation`, `model_version` (optional: `confidence_score`)[cite: 4, 5]. * **Restrictions:** - `risk_score` and `confidence_score` must be numeric within the range $[0, 1]$[cite: 5]. - `priority_level` strictly limited to: `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`[cite: 5]. - Mandatory temporal validation per row: `evidence_start <= evidence_end <= decision_datetime`[cite: 5]. ### B. `evidence.csv` * **Mandatory columns:** `signal_id`, `source_file`, `record_id`, `event_datetime`, `available_datetime`, `evidence_role` (optional: `variable_code`, `contribution`)[cite: 4, 5]. * **Restrictions:** - `evidence_role` strictly limited to: `PRIMARY`, `SUPPORTING`, `CONTEXT`, `QUALITY`[cite: 5]. - Temporal control: `available_datetime <= decision_datetime` of the associated signal[cite: 5]. - **Relational Integrity:** Zero tolerance for orphan signals; every `signal_id` in `signals.csv` must have at least one linked trace in `evidence.csv`[cite: 5].
